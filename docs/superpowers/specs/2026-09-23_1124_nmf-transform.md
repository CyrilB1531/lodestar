# The factorization that could not be applied

**Issue:** [#1124](https://github.com/CyrilB1531/lodestar/issues/1124).
**Status:** written before the work, 2026-09-23.
**Date:** 2026-09-23.

## The problem

`TruncatedSvd` ships `Fit` and `Transform`. `Nmf` ships `Fit` alone, and
`docs/equivalence.md` records the gap as a void whose reason ends "out of scope for 0.1.0" — a
clause naming a version `Lodestar.Decomposition` passed at `0.2.0`. A topic model that cannot
score a document it was not fitted on is the one missing member that stops the type being usable
end to end.

## What was measured

### `NMF.transform` is deterministic, which is the finding that makes this possible

Read out of `sklearn/decomposition/_nmf.py` and then **reproduced**, rather than remembered.
`transform` calls `_fit_transform(X, H=components_, update_H=False)`, and `_check_w_h` initialises
W there without touching `random_state`:

| solver | `W₀` when `update_H=False` |
| --- | --- |
| `mu` | `full(rows × k, sqrt(X.mean() / k))` |
| `cd` | `zeros(rows × k)` |

`X.mean()` is the mean over **every** cell, structural zeros included. The loop that follows is the
ordinary multiplicative update of W with H untouched, the same `max_iter`, and the same
convergence test every tenth iteration.

Re-implemented by hand against `NMF.transform` on the same fit: **maximum deviation 1.7e-16**. So
there is nothing hidden in it, and nothing to seed — unlike `QuantileTransformer`'s `subsample`,
which is why that one is absent and this one can be frozen at decision 0005's `1e-9`.

Degenerate shapes answer rather than refuse: an all-zero matrix gives an all-zero `W` (the mean is
zero, so the fill is zero and the update leaves it), and a zero row inside an ordinary matrix gives
a zero row of `W`. Both losses this package carries, Frobenius and Kullback-Leibler, transform.

### Three of the issue's own sentences do not survive reading the code

- **"coordinate descent with `H` held fixed"** — this package's solver is the **multiplicative
  update**, `MultiplicativeUpdates.UpdateWeights` and `UpdateComponents`, which is scikit-learn's
  `solver='mu'`. Coordinate descent is its `solver='cd'`, which carries Frobenius alone and which
  nothing here implements. `Transform` must use the solver the fit used, so it is the
  multiplicative update with `H` fixed.
- **"honouring the loss and the regularisation the fit was given through `NmfOptions`"** —
  `NmfOptions` carries **no regularisation**: no `alpha_W`, no `alpha_H`, no `l1_ratio`. It honours
  the loss, the iteration cap and the tolerance. The reference defaults its regularisation to zero,
  so there is no divergence to record — only a sentence not to write.
- **`Nmf.Transform(matrix, factorization)`** — `Nmf` *is* the factorization. The shape that matches
  `TruncatedSvd.Transform(CsrMatrix)` is an instance method.

### The one design consequence

`Nmf`'s private constructor keeps the shape, `W`, `H`, `Iterations` and `ReconstructionError`, and
**not the options**. The reference's `transform` replays the estimator's own parameters, so parity
needs the fitted object to remember `BetaLoss`, `MaxIterations` and `Tolerance`.

They are kept **private**. The alternative — an `NmfOptions` parameter on `Transform` — would let a
caller transform under settings the fit never used, which the reference does not permit and which
would read as a feature rather than the silent inconsistency it is.

## What ships

```csharp
namespace Lodestar.Decomposition;

public sealed class Nmf
{
    /// <summary>W for an unseen matrix, with this fit's H held fixed.</summary>
    public double[] Transform(CsrMatrix matrix);
}
```

Row-major, `matrix.RowCount × ComponentCount`, exactly as `TruncatedSvd.Transform` returns its
projection. The refusals are the ones `Fit` and `TruncatedSvd.Transform` already make: a null
matrix, a column count that is not `FeatureCount`, and a stored negative value, `NaN` or infinity.

### What is not written

- **A `Transform` that takes options**, for the reason above.
- **`n_iter_` for the transform.** The reference discards it; this returns `W` alone, and
  `Iterations` keeps meaning what the fit did.
- **The `cd` solver's zero initialisation.** This package has no coordinate descent, so the
  `mu` fill is the only one its `Transform` can have.

## Proof

A third section, `transform`, beside `initialization` and `updates` in
`tests/oracles/decomposition_nmf.json`, frozen from scikit-learn 1.9.1 and compared at `1e-9`.
`tolerance: 0.0` with a fixed `max_iterations`, as the `updates` section already does, so an
iteration count cannot silently differ. It covers both losses, a matrix with fewer rows than the
fit saw, a matrix of all zeros, and a matrix holding a zero row.
