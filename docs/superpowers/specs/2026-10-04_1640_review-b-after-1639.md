# The Review B after #1639: a fit's scratch list let go, saves that search nothing, an index save refused alike

**Issues:** [#1640](https://github.com/CyrilB1531/lodestar/issues/1640),
[#1641](https://github.com/CyrilB1531/lodestar/issues/1641),
[#1642](https://github.com/CyrilB1531/lodestar/issues/1642),
[#1643](https://github.com/CyrilB1531/lodestar/issues/1643).
**Status:** written with the work, 2026-10-04.
**Date:** 2026-10-04.

## The problem

The Review B after #1639, on `main` at `0b99333d`, timed what the earlier reviews had measured in
allocation only, against the latest release — Lodestar.Text 0.7.0 and Lodestar.Embeddings 0.8.0,
"the release" below:

- `EmbeddingIndex.SaveAsync` flushed synchronously before an id longer than ten million
  characters, onto a caller's stream that may refuse synchronous calls (#1640);
- a non-finite index saved to a failing stream raised the stream's exception or the refusal
  depending on the path, sync and async disagreeing (#1641);
- a 4.2 MB `CountVectorizer.LoadAsync` of undeclared length was 15% slower than the release (#1642);
- `CountVectorizer`, `TfidfVectorizer` and asynchronous index saves were 7–39% slower (#1643).

## What the measures found

Stopwatch harnesses drifted by ±10% from run to run, so the decisions rest on BenchmarkDotNet,
the release and this branch built side by side, run interleaved.

- **A fit's scratch list outlived it.** Bisecting the merges since 0.7.0, the 0.7.0 source built
  as a project gave 27.3 ms for the 4 MB load where the merge of #1239 gave 34.7. #1239 had given
  `TextAnalyzer` a `[ThreadStatic]` list of a document's matches, reused across documents; one
  document of 350,000 tokens grew it to 4 MB, which then stayed on the thread, and every later
  operation ran against that heap: 35.4 ms. Without the list held, 27.4.
- **A reader over several segments is slower per token where the heap is large.** With the list let
  go, the #1634 hybrid's mebibyte segments cost the 4 MB load 35–38 ms against the release's 27–28
  in a process that had fitted vectorizers of hundreds of thousands of terms — the realistic one —
  and 38.2 against 36–40 in a process that only loads. One array grown as `MemoryStream` grew it
  gives 27.8 against 27.5 in the first, and 40.9 against 39.7 in the second.
- **What remains is per term, and from main.** About 1% of a load is #1264's code-point order and
  lone-surrogate read, put back to `CompareOrdinal` and `GetString` as a probe only; the 2 MB load
  keeps 3% (10.7 ms against 10.3) with no cause isolated, its growth and copies those of
  `MemoryStream`.
- **The per-term searches cost the saves.** Writing each vocabulary term through `WriteText`,
  which searches it for a lone surrogate (#1263), and measuring each for the writer's ceiling
  (#1618), cost 1–2 ns a term; writing straight through the writer made the same save 5% faster
  than the release.
- **An iterator's locals are fields.** The index head's per-id loop ran inside the iterator that
  yields its flush points; moved into a method of its own, the asynchronous save went from 155 µs
  to 149, 0.8.0's 148.

## Decisions

- **The scratch list is let go past 4,096 matches once a call over its documents ends**, kept for
  the ordinary document it was introduced for, and let go on an exception too (#1643). Let go
  after each document instead, a fit of 200 documents of 20,000 tokens allocated 253 MB against
  the release's 153, the list regrown for each.
- **A load of undeclared length grows one array as `MemoryStream` did until it holds 64 MiB,
  then takes mebibyte segments** — 0.7.0's single array, in time and allocation, below that, and
  segments only where 0.7.0's doubling would allocate hundreds of megabytes (#1642). The
  segment-wise base64 decode #1639 added stays, for the artifacts past 64 MiB.
- **The index head writes its ids in a method the iterator calls**, yielding only where a flush is
  due or an id needs a step of its own (#1643).
- **A vocabulary and an index's ids carry whether any may hold a surrogate and their longest
  length**, found by the fit, the load or the add — free on a load, which notes them as it reads
  each, only an escaped string being able to hold a lone surrogate — so a save writes each
  straight through the writer and measures none unless one may need it (#1643). Handing the
  vocabulary out through `GetFeatureNames`, which a cast can edit, clears what the fit found.
- **An id past ten million characters is preceded by a step**, at which an asynchronous save
  awaits its flush, and written through a `WriteText` that does not flush again (#1640).
- **A synchronous index save points its writer away on a refusal**, as the asynchronous one does:
  nothing pending reaches the stream, and the stream's own failure cannot mask the refusal, sync
  and async alike (#1641, Cyril's call). The vectorizers' synchronous saves do the same, their
  asynchronous ones composing in memory already. A non-writable stream is documented where it is
  refused: once a vectorizer is known fitted, before any string is checked.

## Measured

`ArtifactTimeBenchmarks` (its setup fits vectorizers of up to 350,000 terms) and
`ArtifactLoadOnlyBenchmarks` (no large fit), under `bench/Lodestar.Text.Benchmarks`, built once
against the release from nuget.org and once against this branch, run alternately, two runs each.
BenchmarkDotNet 0.14, default job, .NET 10.0.401, AMD Ryzen 7 8700G, Linux x64, 2026-10-04.
Allocation is per operation; each cell gives both runs' means.

| case | release | this branch |
| --- | --- | --- |
| `CountVectorizer` 240 KB save, sync | 326–347 µs, 505 KB | 286–288 µs, 505 KB |
| `CountVectorizer` 240 KB save, async | 305–315 µs, 740 KB | 285–289 µs, 740 KB |
| `TfidfVectorizer` 45 KB save, sync | 31.9–32.3 µs, 137 KB | 27.6–28.0 µs, 63 KB |
| `TfidfVectorizer` 45 KB save, async | 34.2–34.3 µs, 182 KB | 30.3–30.8 µs, 135 KB |
| `EmbeddingIndex` 942 KB save, sync | 186–190 µs, 244 KB | 165 µs, 244 KB |
| `EmbeddingIndex` 942 KB save, async | 163–165 µs, 244 KB | 164 µs, 244 KB |
| 2.1 MB `LoadAsync`, undeclared, after fits | 15.6–16.8 ms, 21.5 MB | 16.0–16.1 ms, 21.5 MB |
| 4.2 MB `LoadAsync`, undeclared, after fits | 33.1–35.2 ms, 43.9 MB | 33.6–34.2 ms, 43.9 MB |
| 4.2 MB `Load`, undeclared, after fits | 33.1–34.6 ms, 43.9 MB | 32.6–32.7 ms, 43.9 MB |
| 2.1 MB `LoadAsync`, undeclared, load only | 12.7–12.9 ms, 21.6 MB | 12.7–13.0 ms, 21.5 MB |
| 4.2 MB `LoadAsync`, undeclared, load only | 36.3 ms, 43.9 MB | 34.2–37.5 ms, 43.9 MB |
| 4.2 MB `Load`, undeclared, load only | 32.9–35.2 ms, 43.9 MB | 34.0–34.5 ms, 43.9 MB |
| `CountVectorizer.Fit`, 200 documents of 20,000 tokens | 242–245 ms, 152.6 MB | 140–146 ms, 153.1 MB |

The exploratory harness behind the findings above, a scratch project per version, measured `main`
at `0b99333d` too: 240 KB count saves 303–326 µs, the asynchronous index save 178–179 µs, and its
mebibyte segments, the leak fixed, 35.2–38.1 ms for the 4.2 MB load after fits.
