## Problem

`Lodestar.Cluster` is one class, and `docs/equivalence.md` lists DBSCAN as *no counterpart yet*.
Decision 0131 measured the .NET surface: `Dbscan` 3.0.0 is MIT and free, and its `Point` carries
**`X` and `Y` and nothing else**, so a three-feature matrix has nowhere to go; NumFlat's
`Clustering.DbScan` is n-dimensional and ships `net8.0` only. **An n-dimensional DBSCAN is absent
below `net8.0`**, which is the whole claim this class makes.

## What the reference does, measured

Six facts, each probed rather than read, because each is a branch an implementation can get wrong
while passing every well-separated fixture.

1. **`eps` is inclusive.** Three points at `0, 1, 2` with `min_samples=2`: at `eps=0.999` all three
   are noise, at `eps=1.0` they are one cluster. The test is `distance <= eps`, and `<` gives a
   different answer on exactly the fixture a reviewer would build by hand.
2. **`min_samples` counts the point itself.** Two points `0.25` apart at `eps=1`: `min_samples=2`
   makes both core, `min_samples=3` makes both noise. A neighbourhood of size *n* has *n − 1*
   other points.
3. **Clusters are numbered by the first core point in index order**, not by size or position.
   `[[9.0], [9.1], [0.0], [0.1]]` gives `[0 0 1 1]` — the far group is cluster 0 because it is
   first in the matrix.
4. **A border point reachable from two clusters joins the one that reaches it first**, which is the
   one whose lowest-indexed core point comes first. Measured on four orderings of the same nine
   points: with the two dense groups at `0.0–0.3` and `2.3–2.6` and a border at `1.3` within `eps`
   of one core on each side, the border takes label `0` in all four, *whichever* group is first in
   the matrix and *wherever* the border sits — the label follows the growth order, and the border's
   own index is irrelevant. **This is the one place where DBSCAN's answer is not a property of the
   data**, and it is why the corpus freezes four orderings and not one.
5. **`metric="precomputed"` gives the same labels as `metric="euclidean"`** on the distance matrix
   of the same points — the neighbourhood is read off row *i* instead of computed, and nothing else
   changes. The diagonal is a zero distance, so the point is its own neighbour under rule 2 there
   too.
6. **`core_sample_indices_` is ascending**, and holds every core point including those absorbed
   into a cluster started by another.

## Placement

```csharp
public sealed class Dbscan
{
    public static Dbscan Fit(ReadOnlySpan<double> samples, int featureCount, double epsilon, int minimumSamples);
    public static Dbscan FitPrecomputed(ReadOnlySpan<double> distances, int sampleCount, double epsilon, int minimumSamples);

    public static int Noise { get; }                   // -1
    public IReadOnlyList<int> Labels { get; }
    public IReadOnlyList<int> CoreSampleIndices { get; }
    public int ClusterCount { get; }
    public int FeatureCount { get; }
}
```

- **`Dbscan`, not `DBSCAN`.** CA1709 and the framework's own `Rfc2898DeriveBytes` spelling: an
  initialism past two letters is Pascal-cased. `KMeans` beside it is the same rule.
- **Two named factories, not one overload pair.** `Fit` takes a sample matrix and
  `FitPrecomputed` a square distance matrix; both are `ReadOnlySpan<double>` and row-major, so an
  overload set would be distinguished only by the *meaning* of the second `int`. S4136 wants
  adjacent overloads and a reader wants to know which one they called: naming it is the cheaper
  answer, and it matches how `metric="precomputed"` reads at the call site.
- **`epsilon` and `minimumSamples` are plain parameters, and neither is defaulted.** scikit-learn
  defaults `eps=0.5`, which is meaningful only on data already scaled, and a default that is wrong on
  most matrices is worse than no default.
- **Rejected during the work: a `DbscanOptions` record** carrying the two values as `required`
  members, which this spec first proposed. A record of two mandatory values is not an options
  record — `KMeansOptions` earns one with four optional settings — and `required` is used nowhere
  under `src/`, so this lot would have introduced it on `netstandard2.0` for no gain. Four
  parameters are well under S107, and make both values mandatory by construction.
- **`Labels` uses `-1` for noise**, the reference's own sentinel, so
  `Lodestar.Metrics`' silhouette and adjusted Rand read the array unchanged. A nullable `int?` would
  be tidier C# and would break every consumer this package exists to feed.
- **Rejected:** `metric` as an enum over euclidean, manhattan, chebyshev and cosine. Each is a
  different parity target with its own corpus, and cosine in particular disagrees with euclidean on
  the very first fixture probed. The issue scopes it out; a second lot can add them as an overload.
- **Rejected:** a ball-tree or kd-tree neighbour search. It is an optimisation, not a different
  answer — the issue says so — and the benchmark below is what would justify it.
- **Out of scope, from the issue:** `sample_weight`, sparse input.

## The loop

Two passes, no recursion:

1. **Neighbourhoods.** For each row, the indices within `eps`, and whether the count reaches
   `min_samples`. This is the O(n²) pass and the only one that touches the features.
2. **Growth.** Walk the rows ascending; at the first unlabelled core point, open a cluster and
   expand it with an explicit stack, claiming every unlabelled point in a core point's
   neighbourhood and pushing only the core ones. A point already labelled is never relabelled,
   which is fact 4 falling out of the loop rather than being enforced by it.

Noise is `-1` and stays `-1` unless a core point's expansion reaches it, which is the reference's
`dbscan_inner` exactly. The expansion order inside one cluster cannot change a label, so a stack
and a queue give the same answer; the stack is the reference's.

## Evidence

- **`cluster_dbscan.json`**, from `sklearn.cluster.DBSCAN`, **labels compared exactly** — the
  algorithm is deterministic given the neighbourhood order, so a tolerance would be admitting a
  bug. The cases: the `eps` boundary at both sides of it; `min_samples` at the count and one past
  it; the four orderings of the border fixture from fact 4; two and four features; a matrix that is
  all noise; a matrix that is one cluster; duplicate rows; and the precomputed matrix of a case
  already frozen in its euclidean form, so the two paths are compared against each other and not
  only against the reference.
- **Edge tests:** a non-positive or non-finite `epsilon`, a `minimumSamples` below 1, a partial row, a precomputed
  matrix that is not square, and a single sample — which is core when `min_samples` is 1 and noise
  when it is 2.
- **Benchmark:** against **NumFlat 1.3.4**'s `Clustering.DbScan` on n-dimensional input, and
  against **`Dbscan` 3.0.0** on two-dimensional input where it can compete at all — both MIT, both
  read from the artefact. The claim decision 0131 makes is *reach*, not speed, so the table has to
  show what the numbers actually are rather than assume they favour us.
