# The score matrix `Lodestar.Fuzzy` never had

**Issue:** [#1123](https://github.com/CyrilB1531/lodestar/issues/1123).
**Status:** written before the work, 2026-09-23.
**Date:** 2026-09-23.

## The problem

`Lodestar.Fuzzy` ships all seven `fuzz.*` scorers, `Process.Extract` and `Process.ExtractOne`.
`rapidfuzz.process.cdist` — the score matrix of every query against every choice — appears
nowhere, and `docs/equivalence.md` carries no row for it. A caller who has two lists rather than
one query writes the double loop by hand.

## What was measured

### The issue's own reasoning does not survive reading the code

Two of its premises are wrong, and the correction matters because it changes what this member is
for.

- **"the processor `Process.Extract` already takes"** — `Extract` takes no processor. Its
  parameters are `(query, choices, scorer, limit, scoreCutoff)`.
- **"the blocking, the length filter or the score cutoff that `Process.Extract` already does
  inside"** — `Extract` does no blocking and no length filter, and applies the cutoff *after*
  scoring each candidate in full. `docs/equivalence.md`'s existing row says so in as many words.

### What a hand-written loop actually wastes

`Lodestar.Text.Distances.BitParallelLcs` builds a per-pattern equality table (`TryFill`) and then
scans the text against it. Every public entry point takes two strings, so the table is rebuilt on
every call: over a list of choices, once per choice rather than once per query.

A first probe timed one cold pass and read 25.5 ms for 40,000 pairs against the reference's
0.5 ms — a 51× gap that **does not survive a warm-up**. The harness and BenchmarkDotNet agree with
each other and not with it: 1.58 ms and 1.97 ms for the same shape. The cold number was JIT, and
it is recorded here because it is the number this spec was nearly written around.

Warmed, best of five, one 200 × 200 matrix:

| scorer | Lodestar | `rapidfuzz.process.cdist` | ratio |
| --- | ---: | ---: | ---: |
| `ratio` | 1.575 ms | 0.229 ms | **0.15×** |
| `WRatio` | 17.319 ms | 17.658 ms | **1.02×** |

**That contrast is the whole finding, and it is better evidence than any Python-loop comparison.**
The gap lives entirely in the cheapest scorer, where the per-pair table rebuild is most of what a
cell costs; on `WRatio`, which inspects its input and computes several sub-ratios, the fixed cost
is amortised and the two are level. So the deficit is the bulk shape — the table hoisted once per
query — and not the language, which `WRatio` prices at parity.

`workers=-1` is measured *slower* than one thread at this size, which is why the issue is right to
leave parallelism out.

Hoisting the table needs a reusable pattern handle in `Lodestar.Text`, and a branch whose
downstream package needs new upstream API cannot go green (`CONTRIBUTING.md`, *Working across two
packages*). [#1130](https://github.com/CyrilB1531/lodestar/issues/1130) carries that work and the
release order it needs.

### What the reference actually does

Read out of `rapidfuzz` 3.14.6 rather than remembered:

| fact | measured |
| --- | --- |
| default scorer | `fuzz.ratio` — **not** `WRatio`, which is `process.extract`'s default |
| default `dtype` | `np.float32`; `np.float64` available, `np.uint8` rounds to integers |
| `score_cutoff` | **zeroes** a sub-cutoff cell; it does not drop it |
| empty inputs | `(n, 0)` and `(0, m)`, no refusal |
| `workers` | out of scope by the issue's own decision, and measured slower here anyway |

### `Deduplicator` is not expressible over this matrix

Its third scope bullet asks. `Deduplicator.FindClusters` compares **only within blocking buckets**
— sub-quadratic by construction — where a score matrix is quadratic by definition. Expressing one
over the other would throw the blocking away, which is the whole reason that member exists. It
keeps its own pair walk.

## What ships

```csharp
namespace Lodestar.Fuzzy;

public readonly struct ScoreMatrix
{
    public int Rows { get; }
    public int Columns { get; }
    public double this[int row, int column] { get; }
    public ReadOnlySpan<double> Row(int row);
    public double[] ToArray();
}

public static partial class Process
{
    public static ScoreMatrix Cdist(
        IReadOnlyList<string> queries,
        IReadOnlyList<string> choices,
        Func<string, string, double>? scorer = null,
        double scoreCutoff = 0.0);
}
```

`ScoreMatrix` rather than a bare row-major `double[]`: the shape is not an input parameter here as
it is for every bulk member of `Lodestar.Preprocessing`, so a caller given an array would have to
carry the column count beside it. The storage **is** row-major, and the reference page says so, so
`ToArray` hands a caller the layout every other bulk member in this repository uses.

`IReadOnlyList<string>` rather than `IEnumerable<string>`: the choices are walked once per query,
and an enumerable would either be walked repeatedly or materialised silently.

### Three deliberate spellings

- **The default scorer is `Fuzz.Ratio`**, which is `cdist`'s default and **not** `Extract`'s
  `WRatio`. Parity with the reference wins over internal consistency, because a caller porting a
  `cdist` call is the caller this member exists for; the reference page carries the warning in
  bold and `docs/equivalence.md` carries the row.
- **The cutoff zeroes rather than filters**, which is the reference's meaning and the opposite of
  `Extract`'s. A matrix cannot drop a cell.
- **Scores are `double` throughout.** The reference's default `dtype` is `float32`, seven decimal
  digits; the corpus is frozen at `float64` because `1e-9` against a `float32` asserts nothing.

### What is not written

- **`processor`.** `Extract` has none either, and the reference applies it once per element
  rather than once per pair — which is what `queries.Select(processor).ToList()` does at the call
  site, in one line, with the same result.
- **`workers`.** The issue carves it out, and it is measured slower than one thread at the size
  this member is for.
- **`score_hint` and `score_multiplier`.** The first selects a faster implementation inside the
  reference and changes no answer; the second maps a range for memory, which a `double` matrix
  does not need.
- **`dtype`.** One element type, the one every score in this package already is.

## Proof

One corpus, `tests/oracles/process_cdist.json`, frozen from rapidfuzz 3.14.6 at `dtype=float64`
and compared at `1e-9` per decision 0005. It covers all seven scorers, a non-zero cutoff, the two
empty shapes, and text past the BMP through the `TextElement.CodePoint` overloads — the one place
this package's default unit parts from rapidfuzz's, which decision 0001 already decides.
