## The problem

The Review B after #1652, on `main` at `22f31895`, measured main against the latest release —
Lodestar.Text 0.7.0 and Lodestar.Embeddings 0.8.0, "the release" below — and read the token-pattern
and persistence code end to end:

- a pattern .NET refuses, behind a leading `(?u)`, was refused with another message and offset than
  the release's, since #1239 for the word analyzer, `Rake` and `TextRank`, and since #1652 for the
  character analyzers (#1656);
- the vectorizers, `Rake` and `TextRank` refused a pattern with two capturing groups, which the
  release built and read by its whole match, since #1262 (#1651, #1657);
- building a vectorizer with a pattern other than the hand-scanned ones took seven times the
  release's time and nine times its allocation, and so did loading a small artifact holding one
  (#1658);
- `EmbeddingIndex.SaveAsync` of a 942 KB index was 10–17% slower than the release, and the larger
  synchronous saves allocated up to 190 bytes more (#1659);
- found while measuring this branch, `EmbeddingIndex.LoadAsync` of a 100 KB index of undeclared
  length allocated 210 bytes more than the release and ran 5–7% slower (#1661).

## Decisions

- **A refused `(?u)` pattern raises what .NET raises for it as written.** `RefuseAsWritten` parses
  the pattern without its `(?u)`; when that fails, it parses the whole pattern, which .NET refuses at
  the `(?u` itself, and that refusal goes out — the release's type, message and offset.
- **Two groups or more give the whole match.** The release read the whole match whatever the groups;
  one group still gives its text, as `re.findall` does. scikit-learn refuses two, so this is a
  divergence from the reference kept for the release's sake, and `docs/equivalence.md` says so.
- **Construction parses less and compiles nothing.** Three changes, measured one at a time:
  - the pair-aware spelling is parsed with each supplementary set — thousands of units, 30 µs of
    .NET's parser — stood in for by one pair, `TranslateForParse`. A set is an atom in the same
    place either way, so one parses exactly when the other does, and the plain spelling, whose every
    class the stand-in holds in the same place, parses too: a theory over 41 patterns, refused ones
    included, asserts both and the group numbering;
  - both spellings compile at their first use, `Lazy<Regex>`: compiling the plain one at
    construction was 8 µs of the 13 left;
  - the pattern as written is parsed once, by `TextAnalyzer`, and handed to the token pattern, which
    numbers its groups on it: the vectorizer, the analyzer and the token pattern each parsed it.
  `PythonPattern.Compile` and `CompileSurrogateFree`, left to the tests, are gone.
- **The index's head loop is never inlined.** Bisected on `0b99333d`, `6bf7129f` and `22f31895`,
  the asynchronous 942 KB save went 180 → 165 → 181–195 µs, and #1652's iterator-free head was the
  step: with the old iterator restored it was 160–165 again. Inlined into the head written at once,
  `WriteIdsUntilStep`'s loop ran slower; `[MethodImpl(NoInlining)]` gives 156–162 µs. The
  synchronous save writes its head in one loop that flushes where the asynchronous one steps, as
  0.8.0 did, with no iterator.
- **A synchronous save is generic over a struct, not two delegates.** `ArtifactIo.Save` and
  `SaveWithBlock` take an `ISavedArtifact` struct that checks and writes. The releases passed one
  delegate, which .NET 10 keeps off the heap while the save is inlined into its caller; #1641's try
  block stopped that, and the check delegates added more: 64 to 190 bytes on the larger saves. Measured
  once tiered compilation settled — before it, a call allocates what it later does not, and the first
  probes misread that as a regression.
- **A read of undeclared length hands back its one array.** The segment chain built a segment and,
  asynchronously, a second state machine where the release returned its `MemoryStream`'s buffer;
  `Build` now wraps an array with nothing linked, the asynchronous loop is inline, and the chain is a
  struct the read holds.

## Measured against the release

BenchmarkDotNet 0.14, .NET 10.0.401, AMD Ryzen 7 8700G, Linux x64. The release built from nuget.org
and this branch built from the working tree, the in-repo classes and two scratch ones compiled into
both.

| | release | this branch |
| --- | --- | --- |
| `new CountVectorizer(new() { TokenPattern = @"[A-Za-z]\w+" })` | 5.0–5.4 µs, 10.27 KB | 3.1 µs, 9.02 KB |
| same, `Construct` in `TokenPatternBenchmarks`, five patterns | 3.6–6.8 µs, 8.2–11.0 KB | 0.6–3.1 µs, 1.8–9.0 KB |
| `CountVectorizer.Load`, one-document artifact with that pattern | 6.3–6.4 µs, 12.27 KB | 4.1 µs, 11.02 KB |
| `new CountVectorizer()` | 6.7 µs, 11.0 KB | 0.7 µs, 1.84 KB |
| `EmbeddingIndex.SaveAsync`, 942 KB | 155–162 µs, 243.62 KB | 158 µs, 243.62 KB |
| `EmbeddingIndex.Save`, 942 KB | 182–185 µs, 243.5 KB | 159–165 µs, 243.5 KB |
| `CountVectorizer.Save`, 240 KB | 300–306 µs, 504.66 KB | 273–285 µs, 504.67 KB |
| `TfidfVectorizer.Save`, 45 KB | 32.4–33.0 µs, 137.13 KB | 30.0–31.6 µs, 137.13 KB |
| `EmbeddingIndex.LoadAsync`, 100 KB, undeclared length | 98–110 µs, 496.06 KB | 110 µs, 496.09 KB, then the release's bytes once the chain was a struct |

What stays above the release, the first accepted by the maintainer on 2026-10-07:

- **The construction and a first fit together allocate 5–10 KB more** (`ConstructAndFitOneDocument`,
  16.7–24.5 KB against 11.7–14.2), at the release's time: the compiled plain spelling and the two
  parses that check the pattern, where the release compiled the pattern as written once. A fit of
  any size after the first allocates what it did.
- **A synchronous load of undeclared length allocates 40 bytes more**, 179,176 against 179,136 for a
  100 KB index; the asynchronous one allocates what the release does.

A `(?u)`-prefixed pattern that otherwise parses stays accepted, as on main since #1239, where 0.7.0
refused it: it is scikit-learn's own spelling, and the maintainer kept it on 2026-10-07.

## Rejected

- **A cache of parsed patterns.** It would make a repeated construction free, and a benchmark that
  repeats one pattern with it, while a first construction would cost what it did.
- **Dropping the pair-aware parse at construction.** It is what keeps a pattern from failing at the
  first text holding an emoji (#1645); the stand-in keeps that for 1.6 µs of the 30.
