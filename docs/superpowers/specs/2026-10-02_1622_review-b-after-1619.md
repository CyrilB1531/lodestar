## The problem

The Review B after #1619, on `main` at `ed58feb8`, found no defect in what the persistence rework
computes, and five things around it:

- `HashingVectorizer`'s saves refuse a non-finite `MinDf` or `MaxDf`, which its constructor does
  not validate, without documenting it; and a remark said the analyzer goes unvalidated too, where
  every constructor refuses an unknown one (#1622, with four wording items).
- `SaveAsync` copied its `SpillBuffer` out one `WriteAsync` per chunk: 2 writes for a small TF-IDF
  vectorizer and 10 for a 240 KB count vectorizer, where the `MemoryStream` before made one (#1623).
- A load from a stream of undeclared length took its first segment at 81,920 bytes on top of the
  81,920-byte read buffer, about 160 KB for a tiny artifact where the stream before started at 256
  bytes (#1624; measured, 165,952 bytes for a hashing vectorizer).
- `EnsureWritableText` caught the three exception types System.Text.Json 10 was measured to throw,
  so another build's fourth would have escaped undocumented, and a genuine `OutOfMemoryException`
  was worded as an over-long string (#1625).
- No test reached the id and token-pattern refusals, or the TF-IDF order of a vocabulary refusal
  before an idf one (#1626).

## Decisions

- **An artifact under a mebibyte goes out in one write.** The `SpillBuffer`'s first chunk grows as
  the `MemoryStream`'s buffer did — to the larger of what the write needs, twice its length and 256
  bytes, copied over — up to a mebibyte; past it each mebibyte is a chunk of its own, one write
  each, the token passed to every write as main passed it to its single one. Joining small chunks
  into a rented buffer at copy-out was tried and dropped: it held the artifact twice. Doubling from
  256 bytes within one write was dropped too: `AsyncArtifactBenchmarks` measured it at 1,018 KB and
  392 µs for a 240 KB count vectorizer, against 763 KB and 367 µs on `main`.
- **A growing read starts at 256 bytes.** The segments double from there to a mebibyte; the
  81,920-byte read buffer, and with it the byte count a `MaxTotalBytes` refusal names, is main's.
- **Every exception the trial write raises is refused, but cancellation.** The save would raise the
  same one partway through, so none is left undocumented; the message names the writer's exception
  type rather than calling every failure a length, and keeps it as the inner exception.
- **The tests reach each refusal by its message**, the TF-IDF one with a 166,666,667-character term
  fitted and a NaN weight planted, which the vocabulary refusal must win.
- **`JsonArtifact.ReadAllSegmentsAsync` is deleted**, its two test callers moved to
  `ReadWholeAsync`; the class summaries and the remark on the segmented read reach every page that
  shares the behaviour.
- **The refusal's wording covers every failure**: "beyond what the JSON writer can write", in the
  XML documentation, the reference pages and #1618's changelog entries, since a trial that runs out
  of memory is refused too. The netstandard2.0 build of System.Text.Json was not measured: on this
  machine it runs only under .NET 10, whose own writer is the one loaded, and catching every type
  makes its exceptions moot.
- **No changelog entry of its own.** The single write, the 256-byte segment and the catch change
  behaviour #1618 introduced and no release carried; #1618's entries describe the result.

## Measured

`AsyncArtifactBenchmarks`, BenchmarkDotNet 0.14, .NET 10.0.401, AMD Ryzen 7 8700G, 2026-10-03,
run A/B/A under the repository's machine lock — this branch, `main` at `ed58feb8`, this branch:

| row | `main` | this branch |
| --- | ---: | ---: |
| `TfidfSaveAsyncSmall` | 10.57 µs, 17.38 KB | 9.16 µs, 19.15 KB |
| `CountSaveAsyncWide` (240 KB) | 366.8 µs, 763.5 KB | 360.4 µs, 740.6 KB |
| `HashingLoadUndeclared` | 3.78 µs, 162.0 KB | 2.33 µs, 83.2 KB |
| `TfidfLoadUndeclared` | 16.14 µs, 193.1 KB | 15.41 µs, 128.3 KB |

The small save allocates 1.8 KB more: its second flush, ahead of the idf block, doubles the first
chunk as `MemoryStream` doubles its buffer, where `main`'s 256-byte chunks summed to less at that
size; it is 13% faster for making one write instead of two.
